# 备份、导入与迁移

备份入口位于“系统设置 → 站点”。不要只备份一个看起来最大的数据库文件。

## 完整备份

后台完整备份要求主数据库和监控数据库均使用 SQLite。使用外置 MySQL 或 PostgreSQL 时，需使用数据库自身的工具备份外部数据；只复制 Lite 的 `data` 目录不会包含这些历史记录。主数据库为 SQLite、仅指标库外置时，可以另外导出配置包，但它不能代替指标数据库备份。

完整备份用于灾难恢复或迁移整个实例，包含：

- 站点、账号、服务器和任务配置。
- 主数据库与监控数据库。
- 历史监测、延迟、丢包和流量账本。
- 服务器资费版本、账单流水、冲销记录和参考汇率快照。
- 当前版本支持的主题与相关配置。
- 恢复加密两步验证数据所需的实例密钥。

完整备份包含登录配置和实例密钥。持有备份文件的人可以恢复并解密其中的 2FA Secret，因此备份应视为最高敏感级别，通过可信连接下载并加密保存，不要上传到公开网盘或工单。

恢复完整备份、首次安装恢复和主题上传使用分段上传，进度显示已传输字节和百分比。到达 100% 只表示文件已传完，还需等待合并、校验和恢复或安装结果。

当前上传过程中遇到可重试的短暂故障时，会自动重试失败分段；刷新或关闭页面、取消上传、最终失败后重新发起上传，都需要从头传输。下载备份不使用这套分段上传机制，不能据此保证中断后可续传。

Lite 可以恢复 Lite 完整备份，也兼容 Komari 生成的完整备份 ZIP。恢复程序会先识别包结构并完成校验；不要手工改名、重新压缩或删除 ZIP 中看似不需要的文件，否则可能失去迁移所需的版本信息。

Lite `2.3.2` 会在正式替换数据前校验主数据库、监控数据库以及实例密钥与加密 2FA 数据是否匹配。恢复通过后，原账号、密码和 2FA 可以继续使用，但备份中恢复出的旧登录会话会全部失效，需要重新登录。校验或恢复失败时不会把不完整数据作为当前数据使用，应根据页面错误修正备份或磁盘问题后重试。

Docker 使用 bind mount（例如 `./data:/app/data`）时，可以在原挂载目录原位恢复完整备份。恢复前仍应额外复制一份当前 `data` 目录，并确认宿主机目录可写；恢复期间不要让第二个容器同时读写相同目录。

首次安装引导中的备份恢复只出现在第一步“欢迎”。进入管理员、站点、数据存储或确认步骤后，恢复入口会完全隐藏；需要恢复时先返回欢迎页。实例已经初始化后，请使用后台的备份恢复入口。

## 仅导出配置

配置包仍包含账号、实例密钥和部分业务记录，不是脱敏文件，应与完整备份同样保护。

配置包保留服务器、探测任务和必要设置，不包含历史指标、延迟、丢包和流量账本。它适合：

- 从本分支迁往兼容的上游版本。
- 从上游最新版本迁入本分支。
- 复制节点和任务结构到新实例。

这里的“兼容”仅指配置包中目标版本明确支持的字段，不表示完整备份、数据库文件或运行行为完全一致。是否能跨版本导入仍取决于目标版本支持的字段。导入页面会显示校验结果和错误，不应静默丢弃无法识别的关键配置。

## 导入前检查

1. 确认备份来自可信来源。
2. 记录当前版本与目标版本。
3. 先对当前实例做完整备份。
4. 保证磁盘空间能容纳现有数据和导入临时文件。
5. 导入期间不要启动第二个实例读写同一个目录。

## 导入后检查

- 服务器数量、分组及 Agent 是否恢复正常上报。
- 探测任务数量、地址、协议和间隔是否一致。
- 流量限额、重置日、价格和通知设置是否保留。
- 成本中心的资费、月度/年度合计、附加费用和冲销记录是否完整。
- 历史曲线与报告是否符合所选备份类型。
- 主题是否存在且已经启用。

## 直接备份 data 目录

这是最稳妥的冷备份方式：停止 Lite 后复制完整 `data` 目录。目录中的实例密钥必须与数据库一同保留，否则加密的 2FA Secret 可能无法恢复。运行中只复制 `.db` 而漏掉 `-wal` 文件，可能得到时间点不一致的备份。

数据库文件、HTTPS 证书或私钥放在 `data` 目录以外时，需一并单独备份。后台 ZIP 也不包含内置 HTTPS 的证书与私钥；迁移到新主机后，应重新挂载或配置证书路径，再检查 HTTPS。

从上游 `1.4.x` 迁入时，Lite 可以读取 zstd 压缩的指标摘要。兼容读取不等于可以在两个项目之间来回共用同一个数据目录；完成导入后应由 Lite 独占该目录，并在后台检查迁移状态和历史曲线。
