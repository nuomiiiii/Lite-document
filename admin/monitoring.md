# 监测与回程

Lite 的“服务器监控”和“主动探测”是两类数据：前者由 Agent 定时上报，后者由任务按独立间隔执行。

延迟任务和回程任务中的服务器筛选支持多选，已选条件会显示为筛选标签。

## 延迟监测

延迟任务可使用 IPv4 或 IPv6 目标，记录延迟、丢包和可用性。探测间隔越短、关联节点和任务越多、数据保留时间越长，数据库占用通常越高。低频探测已经满足需要时，不建议把间隔设得过短。

新增或编辑任务时可开启“默认开启”。之后新加入的服务器会自动纳入该任务；已经存在的服务器不会因为这个开关被追加或移除。

延迟监测告警的默认配置见 [通知与告警](/admin/notifications)。

## 回程线路监测

回程任务由指定服务器向探测目标执行 ICMP 路由追踪，用于持续识别实际回程线路，并监测线路切换、恢复和持续异常。任务中选择的运营商用于标记探测目标，不会限制实际识别结果；例如电信目标经过移动精品线路时，仍会按实际路径识别。

新增任务时可以一次选择多台探测节点；任务列表支持全选和批量修改目标、周期、运营商、地区及 IP 地址。

### 支持的线路与识别口径

| 运营商 | 可识别线路 |
| --- | --- |
| 中国电信 | CN2 GIA、CN2 GT、163 |
| 中国联通 | CUG VIP（10099 + 9929）、CUG 优化（10099 + 4837）、9929、4837 |
| 中国移动 | CMIN2、CMI、CMNET |

系统按实际路径识别线路，而不是按任务中填写的运营商直接决定结果。联通回程同时经过 10099 和 9929 时识别为 CUG VIP，同时经过 10099 和 4837 时识别为 CUG 优化；电信回程会根据 CN2 后是否转入明确的 163 中间承载区分 CN2 GIA 和 CN2 GT。

“CN2 待确认”和“CUG 待确认”不是线路类型，而是关键跳点隐藏或识别证据不足时显示的过渡状态。它们与“无法识别”一样，不会覆盖上一次已经确认的线路，也不会累计切线或恢复次数。

### IP 疑似被墙判定

Lite 会复用现有回程线路监测，并结合用户选择的延迟监测任务，判断海外节点到中国大陆方向是否同时出现回程路径提前截断和连接丢包。

::: warning 判定结果的含义
“疑似被墙”表示至少两个大陆运营商方向同时出现了持续的路径截断和高丢包，不是对封锁原因的绝对确认。目标主机故障、国内网络大范围异常或特殊路由策略仍可能产生相似现象，应结合监测记录和服务器实际连通性复核。
:::

#### 启用方法

1. 先在“延迟监测”中准备可用于判断节点连通性的任务，并将任务分配给需要判断的海外节点。ICMP、TCP 和 HTTP 任务都可以使用。
2. 进入“回程线路监测 → 监测任务”，为同一海外节点建立至少两个不同运营商的任务，例如中国电信和中国联通。
3. 这些回程任务必须使用相同的地址类型；IPv4 与 IPv6 分开统计，不能互相凑足两个运营商。
4. 编辑每个回程任务，在“判定规则”中开启“参与疑似被墙判定（实验室功能）”，并选择一条已分配给当前节点的“辅助延迟监测任务”。也可以选中多个任务后批量修改。
5. 保存后等待任务采集正常路径基线。需要加快首次采集时，可以在任务列表中手动执行探测，但不要用异常期间的路径建立基线。

功能默认关闭，升级不会自动把已有回程任务加入判定。只有启用回程任务、开启“参与疑似被墙判定”并成功关联辅助延迟任务后，才会参与判断；同一运营商即使建立多条任务，也只按一个运营商方向判断。

建议将 Lite-agent 升级到 `2.3.0.2` 或更高版本。该版本修正了回程线路探测对延迟或无关 ICMP 响应的识别，可减少错误跳点影响判定。

#### 判定说明

系统会结合回程任务和辅助延迟任务近期多个探测周期内的结果进行判断。任务间隔较长时，观察范围也会相应延长。

- 系统会先采集稳定的正常路径。目标不响应 ICMP 时，会使用路径中稳定出现的最深节点作为参考。
- 当前路径仍能进入原有线路或国内汇聚节点，但后续路径相对正常基线持续提前结束时，会先作为路径异常候选。
- 只有路径异常候选与对应辅助延迟任务都满足判定要求，该运营商方向才会记为异常。路径正常但辅助任务高丢包，或路径截断但辅助任务正常，都不会单独触发回程线路异常。
- 辅助任务沿用“延迟监测”已有的丢包结果。ICMP、TCP 或 HTTP 探测失败都会按该任务原有规则计入丢包，但丢包本身仍由延迟监测页面负责展示和告警。
- 同一节点、同一地址类型下至少两个不同运营商方向持续同时异常，并且 Agent 仍在线，才会显示“疑似被墙”；三个运营商同时异常时显示“高置信度疑似被墙”。
- 偶发超时、路径中间短暂丢失响应、探测报错或路径暂时无法比较，不会根据单次结果直接确认。
- 切线优先于疑似被墙。正在确认切线或切线后重新采集基线的任务暂不参与判断。

#### 状态与记录

| 状态 | 含义 | 建议处理 |
| --- | --- | --- |
| 未选择辅助任务 | 已开启功能，但关联任务已删除、取消分配或当前不可用 | 重新选择一条已分配给当前节点的延迟监测任务 |
| 采集判定基线 | 正常路径样本还不足 | 等待至少几轮正常探测，必要时手动执行探测 |
| 判定条件不足 | 同一节点、同一地址类型下不足两个运营商 | 再启用一个不同运营商的任务 |
| 单线路异常 | 只有一个运营商同时出现路径截断和辅助任务高丢包 | 查看路径与对应延迟任务，暂不按疑似被墙处理 |
| 疑似被墙 / 高置信度疑似被墙 | 两个或三个运营商持续同时出现路径截断和辅助任务高丢包 | 结合节点连通性和监测记录复核 |
| 无法判定 | Agent 离线、没有可靠基线或路径无法比较 | 先恢复 Agent 或继续采集基线 |

任务列表可按“疑似被墙”“单线路异常”和“判定条件不足”筛选。将鼠标停在疑似被墙徽章上可以查看异常运营商、路径异常率、辅助任务丢包率和最后正常线路；“监测记录”会保存首次疑似被墙、持续异常和可达性恢复事件。仪表盘的“回程线路状态”也会显示疑似被墙节点数，点击后进入对应筛选结果。

### 状态确认与通知

线路变化达到任务设置的“切线确认次数”后才会确认，重新识别到预期线路后也需要达到“恢复确认次数”。疑似被墙和可达性恢复同样需要连续结果确认；待确认、探测失败或无法识别不会直接改变已确认状态。

回程任务的新建、编辑和批量修改窗口提供四个通知开关：切线通知、线路恢复通知、疑似被墙通知和大陆方向可达性恢复通知。它们共用现有回程线路通知渠道，不需要另建通知规则；关闭通知也不会停止状态判定和监测记录。

持续异常会按任务设置的冷却时间重复提醒。疑似被墙按节点和 IPv4 / IPv6 分别合并通知，多个运营商同时异常只发送一条消息；恢复后只通知一次。消息会包含异常运营商、最后正常线路、路径证据和辅助任务丢包情况，便于继续复核。
